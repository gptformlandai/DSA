HOW TO LISTEN

Welcome. This is your trees series, part one, and we are going to make you fluent in tree recursion by repetition. There is no code in this recording on purpose. Code is for your eyes, on the page. This is for your ears, so the shape of the thinking sinks in while you walk, commute, or rest your eyes.

Here is the promise. By the end of this series, you will not be memorizing individual problems. You will own a single mental template, and you will run that same template against any depth-first tree problem you meet. Pattern recognition is not recognizing the problem. It is recognizing which answer each of six questions takes. The six questions never change. Only the answers change.

Before anything else, let us make sure we share the same simple words, because everything after this depends on them. If you already know these cold, treat the next minute as a warm-up.

A tree is just data shaped like a family tree, drawn upside down. At the top sits one item called the root. Every item in the tree is called a node. Think of a node as a single box that holds a value, and holds two arrows pointing downward, one to a left child and one to a right child. Because each node has at most two children, a left and a right, we call this a binary tree. Binary just means two.

A node's children are the nodes directly below it. The node directly above is its parent. A node with no children, nothing below it, is called a leaf. Picture the leaves at the very bottom edge of the tree. When either arrow points to nothing, we say it points to null. Null simply means empty, nothing there.

Now, a subtree. Pick any node and cover everything except that node and all its descendants below it. That little piece you are looking at is a subtree. The powerful idea of this whole series is that a subtree is just a smaller tree, with its own root, which happens to be that node. So the same logic that works on the big tree works on every subtree inside it.

Two more words. An edge is a single arrow between a parent and a child, one step. The height, or depth, of a tree is how many levels tall it is, how many steps from the top down to the deepest leaf.

And the engine behind all of this is recursion. Recursion is when a function calls itself on a smaller piece of the problem. It sounds circular, but it is not, because each call works on a smaller subtree, and eventually the pieces become so small, an empty node, that the answer is obvious and the calling stops. Here is the mindset that makes recursion click. You do not trace the whole thing in your head. You assume the function already works correctly on the smaller subtrees, you use their answers, and you only reason about one node at a time. That assumption, trusting the smaller calls, is what we will keep calling the leap of faith.

So let us learn the six questions first, because everything hangs off them.

Question one. Parameters. Ask yourself: what must I know from above me, from my ancestors, to do my job? If the answer is yes I need ancestor information, you carry it down as a function parameter.

Question two. Base case. Ask: what is the smallest input where the answer is obvious with no recursion at all? For trees that is almost always the empty node, the null.

Question three. Pre-order work. Ask: is there work I must do before my children run, because it depends on the context handed down from my ancestors? Quick vocabulary here, because you will hear these three words constantly. Pre-order means I do my own work first, before visiting my children. In-order means I visit my left child, then do my own work, then my right child, and for a special kind of tree we will meet later, this produces sorted order. Post-order means I visit both children first, and only then do my own work, using their answers. Pre is before, post is after, in is in-between. That is all those words mean.

Question four. Go left, go right. Ask: what subproblem do I hand each child, and do I trust them to return the right thing? This is the leap of faith. You assume the recursion already works for the smaller subtree.

Question five. Post-order work. Ask: now that both children have answered, how do I combine their answers with myself?

Question six. Return. Ask: what single thing does my parent need from me? And here is the subtle part that separates beginners from pros. What you return to your parent may be different from the global answer you are tracking. Hold that thought. It comes back again and again.

Now, the single biggest idea in the whole subject. There are only two pipes for moving information through a tree. Let me make that concrete before it sounds abstract. Imagine a message can travel two ways in our family tree. A parent can whisper something down to a child before the child starts, that is one direction. Or a child can report something back up to the parent after the child finishes, that is the other direction. Those two directions are the two pipes, and almost every tree problem is really a question of which pipe carries your information.

The down pipe is function parameters. A parent hands context to a child before the child runs. A parameter is just an extra value you pass into the function call, riding along with the node. Think of examples like: the maximum value seen so far on the path, or the legal range a value is allowed to fall inside. Down pipe means pre-order, top-down, ancestor context.

The up pipe is return values. A return value is the answer a function hands back when it finishes. A child hands an answer back to its parent after the child finishes. Think of examples like: the height of my subtree, or, did I find the target somewhere below me. Up pipe means post-order, bottom-up, descendant answers.

And one tattoo for your brain. Parameters only move state downward. They do not carry values back up during backtracking, unless you deliberately pass a shared mutable object, like a list or a hashmap, and clean it up on the way out. Upward data transfer is strictly the job of return values. Mix these two directions up, and every hard tree problem will feel impossible. Keep them straight, and the hard problems dissolve.

That is the entire foundation. Now let us walk the patterns. Same rhythm every time. A story, then the six questions, then the one line that unlocks it, then the classic trap. Feel the repetition. That repetition is the point.


PATTERN ZERO. MAXIMUM DEPTH. THE FOUNDATION.

Every other pattern is a mutation of this one. Master this, and you are more than halfway there.

The story. Imagine you are the boss of a company, and someone asks, how many layers deep is our org chart? You do not count it yourself. You turn to your two direct reports and ask each of them the same question. How deep is your team? You wait for both numbers, take the bigger one, add one for yourself, and report it up. Every manager does the exact same thing. A person with no reports answers zero. That is the whole algorithm.

Now the six questions. Parameters. Do I need anything from my ancestors to compute my depth? No. Depth is about what is below me, not above. So I carry nothing down. Base case. What is the smallest tree where I know the depth instantly? The empty tree. Null returns zero, because null is nothing, zero levels. Pre-order work. Is there work I must do before my kids run? None. I hand my children no context, so there is nothing to prepare. And notice, pre-order being empty is itself a signal. It tells you this is a pure bottom-up problem.

Go left, go right. What do I ask each child, and do I trust the answer? I ask each child for its depth, and yes, I trust it. This is the leap of faith. If you do not trust the recursion for the smaller subtree, you will try to hand-trace the entire tree and drown. Post-order work. Both kids answered. How do I combine them? I take the maximum of the two, the deeper of my two branches, because a depth chain goes through only one side. Return. What does my parent need? The bigger side plus one. The plus one is me.

The line that unlocks it. I do not measure the tree. I ask my children for their depths and just add myself.

Let us trace it once, slowly, out loud, so the leap of faith stops feeling like magic. Picture a tiny tree. At the top, a root, call it A. A has two children, B on the left and C on the right. And B has a single child of its own, D, on its left. That is four nodes. Now watch depth get computed from the bottom up. We call depth on A. A cannot answer yet, so it asks its left child, B. B cannot answer yet either, so it asks its left child, D. D asks its two children, but both are null, empty, so each returns zero. D takes the max of zero and zero, which is zero, and adds one for itself, and returns one. Back up to B. B now has one from its left child D, and its right child is null, which returns zero. B takes the max of one and zero, that is one, adds one for itself, and returns two. Meanwhile C has two null children, so C returns one. Finally, back at the root A. A has two from B on the left, and one from C on the right. A takes the max of two and one, that is two, and adds one for itself. The answer is three. Notice what we did. We never held the whole tree in our head. Each node just trusted its children's numbers and did one tiny addition. That is the entire feeling of tree recursion.

The classic trap. The base case is zero, not one. Null is nothing, not a node.

Three anchor words. Null to zero. Max of left and right. Plus one for me.


PATTERN ONE. DIAMETER OF A BINARY TREE.

This is the first two-brained pattern. The number you return is different from the number you answer. That single idea shows up in half of all hard tree problems, so slow down here.

The story. The diameter is the longest walk between any two nodes, measured in edges. Here is the twist that trips everyone. That longest walk does not have to pass through the root. It could be buried deep in one branch. So you cannot just measure from the top. Instead, you stand at every node and ask, if the longest path bends right here at me, going down my left side, through me, and down my right side, how long is it? You quietly remember the biggest such bend you have ever seen. That remembered maximum is the answer.

The six questions. Parameters. Ancestor info? No, just the node. The running best diameter lives outside the recursion, because many different nodes each produce a candidate, and we want the maximum across all of them. Base case. Null returns height zero, so a leaf sees zero from both sides. Pre-order. None, pure bottom-up. Go left, go right. I get each child's height, because the path bending at me is built from how deep I can reach on each side.

Post-order, the key. The path that bends at me spans left height plus right height edges. I update my global maximum with that sum. I record the best I have ever seen, because the true diameter might bend at some other node, not me. Return, the other half of the key. Does my parent want that same sum? No. I return one plus the taller of my two arms. Here is why. My parent wants to extend a path through me and keep going up, but a path cannot fork. It can pass through me using only one of my arms. So upward I offer just my taller arm plus myself. The both-arms sum was a terminal answer. The path ends by bending here, so it can never be extended, so it never travels up.

The line that unlocks it. At each node I answer with both sides added, the bend, but I return only one side plus me, because my parent's path cannot fork through me.

The classic trap. Returning the bend upward instead of one plus the max side. If you return the bend, you are claiming a parent can walk down both your arms at once. Impossible. The bend is the answer. One plus max is the return. Two separate buckets.

Three anchor words. Answer is left plus right. Return is one plus max. A path cannot fork.


PATTERN TWO. COUNT GOOD NODES. THE TOP-DOWN, PARAMETER PATTERN.

This is the mirror image of diameter. Diameter used the up pipe. Good nodes uses the down pipe, parameters. This is where you truly feel the difference between the two directions.

The story. Walk from the root down any path. A node is good if, on the way from the root to that node, nobody you passed was bigger than you. In other words, you are good if you are the tallest person seen so far on your root-to-you path. So as you descend, you carry a running value, the maximum I have seen so far. At each node you check, am I at least that max? If yes, you are good, count yourself. Then you pass an updated max down to your children.

The six questions. Parameters, the key. Do I need anything from my ancestors to judge myself? Yes. I carry the largest value on the path from the root down to my parent. Good is defined relative to who came before me, and that information lives above me, so a parent must hand it down as a parameter. This is the moment the answer to question one flips from no, in depth and diameter, to yes. When the definition mentions ancestors, or the path from the root, or so far, question one is always yes, and you reach for a parameter.

Base case. Null returns zero, an empty spot has no node to be good. Pre-order work, also the key. Before recursing, I do two things using the ancestor context I was handed. First, I judge myself. Am I at least the max so far? Second, I build the updated max to pass down, the larger of the old max and my own value. My children's max so far must include me, so I compute it before calling them. And the rule of thumb here is golden. Work that depends on ancestors happens in pre-order. Work that depends on descendants happens in post-order.

Go left, go right. I hand both children the updated max. Post-order. I add the two children's counts. Return. My own goodness plus both subtree totals.

The line that unlocks it. I judge myself using state my parent handed me, then I hand an updated version of that state to my kids. Down pipe, pre-order.

The classic trap. Trying to compute good in post-order, after the children. You cannot. Goodness depends on ancestors, which are only known on the way down. If you ever find yourself needing ancestor info, that is your signal. Use a parameter, do the work in pre-order.

The twin comparison, say it out loud. Good nodes needs ancestor info, so push down via parameter, pre-order. Diameter and depth need descendant info, so pull up via return, post-order. From the root, on the path so far, ancestor, means down. Height, deepest, longest below, subtree, means up.

Three anchor words. Carry max so far down. Judge in pre-order. Ancestor means parameter.


PATTERN THREE. THE STRUCTURAL TRIO. INVERT, SAME TREE, AND MIRROR.

Three problems, one family. Grouping them shows the resemblance so they stop cluttering your brain.

First, invert a binary tree. The story. Hold the tree up to a mirror. Every left child becomes a right child, and vice versa, all the way down. At each node you just swap your two children, then tell both children to do the same to themselves. Quickly through the questions. No ancestor info. Base case, null returns null, an empty tree mirrored is still empty. The work is simply, swap my two kids, then recurse into both, then return myself now mirrored. The line. Invert equals swap my two kids, then ask both kids to invert themselves.

Now the pair, same tree and mirror, and here is the new move. The recursion walks two nodes at once. The function takes two node arguments and steps them in lockstep.

The story. Same tree. Put two trees side by side. Are they identical? Check the two roots match, then check left against left and right against right. Mirror, also called symmetric. Is one tree the mirror of the other? Check the two roots match, then check left against right and right against left. The cross. That single flip, left with right, is the only difference between same and mirror.

The six questions, two-node version. Parameters. What do I carry? Two nodes, one from each side. The question is about a relationship between two positions, so I hold both at once. That is the tell for comparison problems. Base case, and order matters. If both are null, true. If exactly one is null, false. Only after those null checks do you compare values. Pre-order. Compare the two current values, fail fast if they disagree. Go left, go right, the pattern-defining question. How do I pair the children? For same tree, left with left, right with right. For mirror, left with right, right with left, the cross. Post-order. Combine the two child booleans with a logical and. A boolean is just a true-or-false value, and a logical and means the result is true only when both parts are true. Return. Send that and upward.

The line that unlocks it. Same tree and mirror are the same code. The only difference is that mirror crosses the recursive calls, left with right.

The classic trap. Checking the values before the null checks. If one node is null, reading its value crashes. Always do the null base cases first, values after.

Three anchors for the trio. Invert is swap kids. Same is left-left, right-right. Mirror is left-right, right-left, the cross.


PATTERN FOUR. LOWEST COMMON ANCESTOR. THE L C A.

The famous return-a-node pattern. The return value is a node, and its meaning shifts depending on where you are. Read this one slowly.

The story. Two cousins, call them p and q, are lost somewhere in a family tree. You want the lowest, the closest, shared ancestor. Here is the elegant trick. Every node asks its two subtrees, did you find either p or q down there? If your left subtree reports I found one, and your right subtree reports I found one, then p and q are on opposite sides of you, so you are the meeting point. You are the lowest common ancestor. If only one side reports a find, the answer is somewhere on that side, so you simply pass that finding upward.

The six questions. Parameters. I carry the node plus the two targets, p and q. Every frame must know what it is hunting for. The targets ride along, read-only. Base case. Null returns null, nothing here. And if the current node is p or q, return the node itself, meaning, I found a target, stop and report me up. Pre-order. That found-check is the pre-order judgment. Go left, go right. Each side returns either a found node, or the confirmed answer, or null. I need to know which sides contain a target.

Post-order, the key. If left is non-null and right is non-null, the two targets were found on opposite sides of me, so I am the answer. Return the current node. Return. Otherwise, return whichever side is non-null, bubbling the single find upward. If both are null, return null. Notice the return slot carries two meanings. Low down it means, a found target. Once both sides meet, it means, the confirmed lowest common ancestor. Same slot, layered meaning.

The line that unlocks it. If p and q come back from opposite sides of me, I am the meeting point. Otherwise I just forward whichever child found something.

The classic trap. Returning the left result before checking whether the right is also non-null. If both are non-null, you must return the current node, not just the left. Always test both sides non-null first.

A shortcut worth mentioning. In a binary search tree, the L C A is even simpler. Walk down. If both targets are smaller than the node, go left. If both are larger, go right. The moment they split, or one equals the node, that node is the L C A. This takes order h steps, and let me unpack that phrase, because it returns often. When we say order something, we mean roughly how the work grows as the tree gets bigger. Order n means the work grows in step with the number of nodes, so touching every node. Order h means the work grows only with the height of the tree, the number of levels, which is far smaller, because you follow a single path from top to bottom instead of visiting everything. So order h is fast. No post-order needed here.

Three anchor words. Node equals target, return node. Both sides non-null, I am the L C A. Otherwise bubble up.


PATTERN FIVE. INORDER SUCCESSOR IN A BINARY SEARCH TREE. THE NEXT BIGGER NODE.

This is the walk-in-sorted-order pattern. It leans on the golden fact of binary search trees. First, what is a binary search tree, often shortened to B S T? It is a binary tree with one extra rule: for every node, everything in its left subtree is smaller than it, and everything in its right subtree is larger. That ordering rule is powerful, and here is its most famous consequence. An inorder traversal of a B S T, remember, that is left, then node, then right, produces the values in ascending sorted order, smallest to largest.

The story. Line everyone up in sorted order. That is exactly what an inorder traversal gives you. The inorder successor of a node p is simply the very next person in that sorted line. The smallest value that is still strictly greater than p.

Now, this one bends the template. It is a directed walk, like binary search, not a two-child recursion. Seeing how the same six questions still apply is the lesson. Parameters. What state must survive the walk down? The node, the target p, and a running candidate, the best successor found so far. As I descend, I carry the best-so-far like a torch. The tree's sorted shape is my ancestor context. Base case. When I fall off the tree, when the node is null, I stop, and the candidate holds the answer. Pre-order. At each node I compare its value to p, and I choose a direction. That comparison uses only the current node and the target, no child info, so it belongs before any descent.

Go left, or go right, but only one side. If the node is bigger than p, this node could be the successor, so I record it as the candidate, then I go left to hunt for a smaller-yet-still-bigger value. Otherwise, the node is too small or equal, so I go right and record nothing. This one-sided move is the crucial deviation. The B S T order lets me prune an entire half at each step, which is why it is order h, not order n. Post-order. None. The answer is captured on the way down, not assembled from children. Return. The candidate, the smallest value that was still strictly greater than p.

There is a second flavor worth knowing, when the node carries a parent pointer. If p has a right subtree, the successor is the leftmost, the smallest, node of that right subtree. Go right once, then all the way left. If p has no right subtree, the successor is the lowest ancestor for which p sits in the left subtree. You climb up through parents until you move up and to the right.

The line that unlocks it. The successor is the smallest value still bigger than me. In a B S T I binary-search downward, remembering the last node bigger than p, and that last remembered one is the answer.

The classic trap. Two of them. Forgetting the no-right-subtree case, where you must climb the ancestors. And using greater-than-or-equal instead of strictly greater-than. The successor must be strictly greater.

Three anchor words. Next in the sorted line. If a right subtree exists, leftmost of the right. Otherwise climb up and to the right.
